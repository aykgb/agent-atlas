# 刷新数据耗时优化

## 诊断

“刷新数据”依次执行本机增量索引、所有启用远端的同步，再重载当前页面。

2026-11-16 本机实测：完整 `POST /api/refresh` 为 15.28 秒；文件扫描约 48 毫秒，三个远端的用量导出分别约 0.35～0.45 秒。本机索引副本的性能剖析显示，OpenCode 数据库时间戳变化触发了全部 1,463 个轮次重写，全文索引写入与时间转换占据主要耗时。无文件变化时，原实现仍重算两张用量汇总表。

## 方案

- 没有变化文件时直接返回，不写索引、不重算汇总、不改变数据更新时间。
- 对有变化的文件仍完整解析；按轮次比较内容与词频，只更新新增、改写或删除的轮次。文件用量独立替换，未变轮次及全文索引直接复用。
- 既有轮次或其词频被修改、删除时，更换导出指纹的修订标记，使任意游标的探针均能检测历史变化并全量重拉；沿用原接口字段，旧版同步方也适用。
- 本机刷新合为一个事务，更新抛出异常时整次回滚。
- 数值时间戳先作为 UTC（协调世界时）解析，再转换为本地时区，省去重复的本地时区解析；日期归属与夏令时规则保持一致。
- 独立远端最多四台并行同步，返回顺序与配置一致；每台保留原有事务、失败状态及旧数据保留机制。
- 远端游标探针失效时仍全量拉取核对，但按内容签名复用未变轮次的全文索引；词频单独比较，删除不再存在的轮次，避免历史小改动导致整库重新索引。
- 自动检查直接复用增量更新的无变化路径，避免重复扫描。

## 验收

1. 同一索引快照对比优化前后本机刷新耗时，核对轮次、搜索、词频与两张用量表一致。
2. 无变化刷新不改索引；只触碰文件时间戳时保留轮次标识与全文索引；实际追加、改写与删除仍更新搜索、词频和用量。
3. 数值与字符串时间戳的结果一致，覆盖夏令时转换与非法输入。
4. 多远端确实并行、返回顺序稳定，单台失败不影响其他远端。
5. 运行全部契约测试与前端语法检查，再实测运行中服务的完整刷新。

## 实测

### 固定快照对照

本机对照使用同一份索引基线和冻结的两份变化日志，分词词典预热后分别运行旧、新实现；包含解析与索引写入，不包含文件扫描、远端同步和页面重载。

| 场景 | 优化前 | 优化后 | 结果 |
| --- | --- | --- | --- |
| 本机两个变化文件的解析与增量索引 | 15.185 秒 | 4.665 秒 | 减少约 69% |
| 远端游标失效，固定 415 个轮次的同步处理（不含网络） | 2.837 秒 | 0.364 秒 | 减少约 87% |

本机 `turns` 3,066 行、`terms` 32,424 行、`usage` 282 行、`session_usage` 749 行、`file_usage` 30,194 行逐项摘要一致；长词、中文短词搜索命中数一致。远端对照的轮次、词频、两张用量表及搜索结果也一致。

### 运行中服务

- 优化前完整 `POST /api/refresh` 为 15.279 秒，三个远端均成功。
- 首次应用本机优化时，`mini` 恰好发生历史轮次更新，触发全量重拉，完整请求为 61.194 秒，三个远端仍均成功。随后单独读取其约 31.38 MB 的完整导出花费 41.858 秒；全量重拉仍受当前网络与远端导出协议限制，索引复用不能省掉这部分传输。
- 最终版本首次完整刷新为 71.198 秒，`mini` 的历史更新再次触发大体积全量传输；三个远端均成功。随后在已同步状态下完整刷新为 **3.432 秒**，HTTP 200，三个远端分别 415、838、1,688 个轮次，错误均为空。日常刷新样本相比原来的 15.279 秒减少约 78%，两次实测期间日志有自然增长；严格的新旧耗时对照见上方固定快照表。
- 服务重启后再次确认持续运行，地址 `http://127.0.0.1:18763`。

### 自动检查

- `.venv/bin/python -m unittest discover -s tests -v`：69 项全部通过，覆盖历史轮次变化使任意游标探针失效、远端重拉复用未变标识、词频资格变化，以及重拉中途失败回滚。
- `node --check static/app.js` 与 `git diff --check` 通过。
